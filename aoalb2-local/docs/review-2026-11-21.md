# レビュー指摘への対応（2026-11-21）

GitHubへのpushは行っていない。計測はLinux（2コア・メモリ8GB）。Windows（WebView2）での計測はワークフローに組み込み済みで、push後に Actions Artifact として得られる（未実施）。

## 1. 古いバックアップへの復元で写真が黙って消えないこと【修正】

- 原寸写真は作成後に削除しないため、古い世代へ復元すると「原寸はあるが一覧にない写真」になる。従来はこれが黙って一覧から外れていた。
- 修正：`backup::restore` の最後で **自動的に `recover::recover_unregistered` を実行**し、結果（件数）を `RestoreReport.recovery` として画面へ返す。画面は「写真を一覧へ戻しました：○枚」を表示する。
- 戻し方：直前に自動で作った「復元の前」バックアップを含め、**バックアップを新しい順に探し、同じ写真ID・同じSHA-256の記録があれば、その記録をそのまま戻す**（aoPIC元情報・元分類・分類の上書き・撮影日時・写真番号・取込み記録）。
- 台帳の配置は、復元した時点の状態になる（復元前の配置は「復元の前」バックアップに残る）。
- 検証：`restore_old_backup_keeps_later_photos`（バックアップ後に取り込んだ aoPIC 3枚＋一般2枚、分類の上書き、台帳配置 → 古い世代へ復元 → 7枚すべて一覧に残り、5枚はバックアップの記録から戻り、aoPIC情報・上書きも一致、再オープン時の未登録0）。

## 2. DBに登録されていない originals の検出・復旧【追加】

- 検出：**工事を開くたびに** originals/ のファイル名（`{写真ID}.jpg`）とDBを突き合わせ、未登録数を `OpenReport.unregisteredOriginals` で返す（3,000枚でも数十ms）。画面は「一覧にない写真が○枚あります［一覧へ戻す］」を表示。「バックアップ・復元」画面にも「一覧にない写真を探す」を追加。
- 復旧（`recover::recover_unregistered`）：
  1. 先に「写真の復旧の前」バックアップを作る
  2. 各ファイルのSHA-256を計算
  3. バックアップ（新しい順・同じ工事・同じスキーマ版のみ）に同じID・同じSHA-256の記録があれば、それを戻す
  4. どこにもなければ、ファイルのJPEGヘッダー・EXIFから一般写真「復旧した写真」として登録（撮影日時・向きは保持、分類は未分類）
  5. 写真として読めないファイルは「復旧できなかった写真」として報告し、**削除・移動しない**。アプリが作った形式ではないファイル（`memo.txt` 等）は数えるだけで触らない
  6. photoUid が既に別の写真で使われている場合は photoUid を空にして登録（元の値は aoPIC 元情報に残る）
- 検証：`unregistered_originals_detect_and_recover_from_file`（異常終了相当の未登録JPEG・壊れたファイル・利用者のファイル → 検出2件、ファイルから1件復旧、1件失敗、他ファイル1件、原寸のSHA-256不変、復旧前バックアップあり）。

## 3. 日本語フォントがない端末でもPDFの文字を保証【修正】

- 従来は端末のフォントを探し、なければ閲覧ソフト任せ（非埋込み）だった。
- 修正：**BIZ UDゴシック Regular をアプリ本体に組み込み、常にそれを使う**（端末のフォントは一切使わない）。使った文字だけを抜き出して埋め込み（CID TrueType、Identity-H）、コピー・検索用の文字対応表も付ける。
- 収録外の文字（BMP外の漢字「𠮷」、絵文字、外字）は「〓」にし、PDF作成結果に「印刷できない文字が○種類あり〓で表示しています：…」と警告する。
- 確認：
  - 自動検証 `pdf_embeds_jpeg_without_recompression`：同梱フォント名、`/FontFile2` の存在、非埋込みフォント指定がないこと、「髙・﨑・①・㈱」は警告されず「𠮷・😀」は警告されること。
  - 端末フォント0個の環境（fontconfig のフォント0件）で pdftoppm により描画し、「髙﨑①㈱」を含め正しく表示されることを目視確認。`pdffonts` の結果は `CID TrueType / Identity-H / emb yes / sub yes / uni yes`。
- 収録範囲：JIS X 0208 の6,879字すべて。CP932では外字（利用者定義領域1,880字）以外すべて。

## 5. 3,000枚時のメモリ（画面エンジンを含むアプリ全体）【計測・修正】

計測方法：アプリを環境変数 `AOALB2_E2E_PROJECT`／`AOALB2_E2E_OUT` 付きで起動すると、アプリ自身が「工事を開く → 写真一覧3,000枚を端までスクロール → 全選択 → 1,000ページの台帳を開いて端までスクロール」を行い、終了する（環境変数がなければ何もしない）。外側のスクリプトが、アプリと画面エンジンの全プロセスのメモリを0.5秒ごとに記録する（Linux：`scripts/measure-app-memory.sh`、Windows：`scripts/measure-app-memory.ps1`）。

**計測で見つかった問題と修正**
1. 台帳編集画面が、一度表示したページを消さなかった（1,000ページ全部・画像3,000枚がDOMに残った）→ 画面から離れたページは画像ごと解放する。
2. サムネイルを `<img>` で表示していたため、画面エンジンの画像キャッシュに溜まり続けた → **読み込み→表示サイズに縮小してcanvasへ描画→元データをすぐ解放**する方式に変更（同時読込み6枚、画面外は中止）。
3. 画像を汎用のファイル配信（どのファイルでも許可範囲なら読める）から、**今開いている工事の `写真ID.jpg` だけを返す専用の経路**（no-store 付き）へ変更。汎用配信は無効化。

**Tauri アプリ全体（Linux・WebKitGTK）**：実サムネイル3,000枚。PSS＝共有部分を按分した実使用量

| 区間 | 修正前 PSS／RSS | 修正後 PSS／RSS |
|---|---|---|
| 起動〜一覧表示 | 450／635MB | 423／615MB |
| 一覧を端までスクロール | 760／927MB | 538／713MB |
| 1,000ページ台帳を端までスクロール | **992／1,158MB** | **580／754MB** |
| 画面上の要素（一覧／台帳） | 96枚／1,001ページ・画像3,000 | 96枚／6ページ・画像6 |

修正後のプロセス別最大（PSS）：中核と画面の窓 110MB、画面エンジン 440MB、通信プロセス 31MB、GStreamer部品の検査 85MB（WebKitGTK固有。Windowsにはない）。

**Chromium（WebView2と同じ系統）での同じ操作**（ブラウザ全プロセス、`app/tests/chromium-memory.mjs`）

| 区間 | 修正前 PSS | 修正後 PSS |
|---|---|---|
| 一覧表示 | 424MB | 444MB |
| 一覧を端までスクロール後 | 792MB | 493MB |
| 台帳を端までスクロール後 | **1,183MB** | **504MB**（最大514MB） |

- WebView2 での実測：`.github/workflows/aoalb2-local-windows.yml` がインストーラー作成後に同じ自動操作を `aoalb2-app.exe` で実行し、`aoalb2-app` と子プロセス（msedgewebview2 を含む）の WorkingSet／Private を記録して Artifact に入れる。**push前のため未実施。**

## 6. 1,001ページPDF

| 写真 | 原寸合計 | 出力容量 | 所要時間 | 最大メモリ（工程中） | 原寸のデコード |
|---|---|---|---|---|---|
| 実容量相当（一般2,100枚×約2.2MB＋aoPIC 900枚） | 4,470MB | **4,473MB** | 8.0秒 | 88MB（工程開始時83MB） | 0枚 |
| 軽い架空写真（一般×約0.57MB） | 1,211MB | 1,214MB | 1.8秒 | 83MB（同79MB） | 0枚 |

- 実JPEGの使用：**実際の現場写真は使っていない**（リポジトリに実写真を入れない方針のため）。一般写真は、圧縮が効きにくい細かい模様を入れた 4000×3000 の生成JPEG（約2.2MB、12MPスマホ・コンデジ相当）。aoPIC写真は 1280×960 の生成JPEG。いずれもJPEGとして正しく、PDFへは原寸のバイト列をそのまま埋め込んでいる（自動検証でバイト一致を確認）。
- 出力容量は原寸合計とほぼ同じ（再圧縮しないため）。5MBのデジカメ写真3,000枚なら約15GBのPDFになる。大きな台帳は分割出力、または印刷用の縮小画像の採用を検討事項とする（原寸は不変のまま）。
- 最大メモリ：「工程開始時」は計測ツールが写真を生成した分を含む。PDF工程による増加は5MB以下（1ページずつ書き、写真は1枚ずつ読んで書くだけ）。

## 7. 4.3GB引継ぎ試験（`examples/huge_exchange.rs`）

| 工程 | 所要時間 | 最大メモリ |
|---|---|---|
| 取込み（約95MBの写真×46枚） | 11.0秒 | 101MB※ |
| 書出し＋書き出したファイルの全件SHA-256再検証 | 11.4秒 | 7MB |
| 別フォルダへの取込み（全検証・確定） | 10.8秒 | 7MB |

- 原寸合計 4,583,367,954バイト、引継ぎファイル **4,583,385,984バイト**（圧縮後／原寸＝1.0000。JPEGは圧縮しても小さくならないため無圧縮で格納、差は管理情報の約18KB）。ZIP64で作成。
- ※取込みの101MBは、計測用に95MBの写真データを作る処理を同じプロセスで行った分。
- 自動検証 `huge_exchange_over_4gb` も合格（生成込みで37秒）。

## 8. GitHub Actions の権限と影響範囲

- 実行条件：`feature/aoalb2-local` への push だけ（main・タグ・Pull Request・スケジュール・手動実行では動かない）。
- 権限：ワークフローとジョブの両方で `permissions: contents: read` のみ。
- `actions/checkout` は `persist-credentials: false`（取得後に資格情報を残さない）。
- secrets を一切参照しない（Supabase 等の鍵に触れない）。外部サービスへ接続する処理もない。
- Release 作成・GitHub Pages・main への書込み・タグ作成をする手順はない。
- 外部 Action はコミットSHAで固定（checkout・setup-node・upload-artifact・rust-toolchain・rust-cache）。
- 同じブランチの実行が重なった場合は古い方を中止。最長120分。

## 9. Windows向け成果物

- `actions/upload-artifact` だけで保存（保存期間7日、ファイルがなければ失敗にする）。
- 内容：未署名インストーラー（NSIS）、3,000枚の計測結果、WebView2を含むメモリ計測結果。
- 自動更新は無効（`createUpdaterArtifacts: false`、更新プラグインなし）。
